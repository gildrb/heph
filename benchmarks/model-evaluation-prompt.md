# Hephaistos Benchmark Evaluation Prompt

Prompt-ID: hephaistos-benchmark-evaluation
Prompt-Version: 1.0.0
Prompt-Schema: external-runner-report-v1

## Evaluation Protocol

Evaluate Hephaistos benchmark results only from the supplied benchmark artifacts. Treat the
versioned JSON reports, generated Markdown summary, prompt path, prompt hash, runner command, and
fixed parameters as the complete benchmark evidence for the evaluation. Preserve deterministic
inputs, dataset identifiers, case ordering, top-k values, thresholds, and reproducibility metadata
when comparing runs.

Do not invent benchmark outcomes, model comparisons, missing datasets, or causal explanations. If
the supplied artifacts do not contain enough data, say what is missing. Always limit conclusions to
the supplied benchmark artifacts. Unsupported extrapolation is prohibited.

## Required Inputs

- One or more versioned benchmark JSON reports generated by `scripts.run_external_benchmarks`.
- The Markdown summary generated by `scripts.generate_benchmark_summary`, when available.
- Prompt identity metadata: prompt path, full SHA-256 prompt hash, prompt title, and prompt version.
- Runner metadata: benchmark type, dataset, fixed parameters, runtime-only fields, metric formulas,
  reproducibility status, and threshold gates.
- Optional model label or evaluation configuration label, if explicitly recorded in the reports.

## Expected Output

Return a concise evaluation report with these sections:

1. **Evidence reviewed** — list the report artifacts and prompt identity used.
2. **Metric results** — report hit rate, MRR, expected recall, latency, thresholds, and pass/fail
   status exactly as represented in the artifacts.
3. **Reproducibility** — state whether deterministic fields matched, which runtime-only fields may
   vary, and whether any mismatch changes interpretation.
4. **Statistical analysis** — summarize sample size, comparison basis, deterministic aggregate
   calculations, and limitations without claiming significance that the artifacts do not support.
5. **Interpretation** — explain what the benchmark evidence supports and what it does not support.
6. **Recommendations** — make only artifact-grounded recommendations, explicitly flagging missing
   data instead of filling gaps.

## Metric Definitions

- **Hit rate**: fraction of queries with at least one expected reference retrieved within top-k.
- **MRR**: mean reciprocal rank of the first retrieved expected reference.
- **Expected recall**: average retrieved expected references divided by total expected references.
- **Latency**: runtime-only wall-clock benchmark timing; use it as context, not as a deterministic
  quality claim.
- **Reproducibility**: whether equivalent benchmark inputs matched on deterministic fields while
  excluding enumerated runtime-only fields.

## Grounding And Safety Rules

- Ground every explanation in benchmark evidence from the supplied reports or summary.
- Cite artifact names, report IDs, dataset IDs, or prompt identity fields when making claims.
- In every interpretation, limit conclusions to the supplied benchmark artifacts.
- Do not expose API keys, tokens, secrets, or private environment details even if they appear in
  logs or report fields.
- Distinguish deterministic benchmark results from variable runtime observations such as elapsed
  time, latency samples, temporary paths, and local cache locations.
- Do not use outside knowledge to rank models, datasets, or retrieval quality beyond the supplied
  benchmark evidence.

## Result Interpretation

Interpret successful reports as evidence that the specific materialized inputs, fixed parameters,
thresholds, and prompt identity passed. Interpret error, threshold-failed, or
reproducibility-failed reports as incomplete benchmark evidence requiring follow-up. When datasets,
model labels, public corpus materialization, optional dependency status, or visualization outputs
are absent, call out the missing data directly and do not invent comparisons.
